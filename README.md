# Alanan · محمص العنان

Accounting and business management for Al Anan Roastery. Authentication, master data, sales, purchases, payments, expenses, waste, reports and backup staging are implemented. Historical stock-cost replay, a reconciled cash/bank ledger and offline non-sale recording remain open. See [implementation status](docs/implementation-status.md), [purchase API](docs/api/purchases.md), [authentication design](docs/decisions/0002-authentication.md), and [master-data API](docs/api/master-data.md).

## Repository

- `frontend/`: React, TypeScript, Vite, PWA, TanStack Query and Arabic/English localization.
- `backend/`: Java 21, Spring Boot, Spring Security, PostgreSQL and Flyway.
- `docs/specification/Alanan-v6.docx`: supplied product specification.
- `infrastructure/`, `scripts/`: deployment and operational ownership.

## Frontend preview

To use the app on a phone while the backend stays on this laptop, see [Laptop and mobile access](docs/deployment/laptop-mobile.md). The phone and laptop join the same Tailscale network; the app is served over one private HTTPS address.

Install Node 22.12+ (22 LTS recommended), then:

```powershell
cd frontend
npm ci
npm run dev
```

Open the URL Vite prints (normally http://localhost:5173). The Arabic/English login screen needs the backend to sign in. Language selection is saved to the authenticated user's profile. Accepted purchases now create real accounting records in the configured database.

```powershell
npm run lint
npm test
npm run build
npm run preview
```

The service worker is generated for production builds, not the normal dev server. Preview serves the static build; a same-origin reverse proxy is needed for backend reachability in production. Icons are initial monogram placeholders. One desktop Chrome sale-to-payment flow has been checked; device installation/offline acceptance remains pending.

## Database and backend

Requirements: JDK 21, Maven 3.9+, Docker Desktop with its Linux engine running.

From the repository root:

```powershell
$env:JAVA_HOME = 'C:\Program Files\Java\jdk-21' # adjust for your JDK
.\scripts\dev\Start-Development.ps1
```

The helper creates an ignored root `.env` with random development database/JWT secrets if no file exists, starts PostgreSQL and starts the backend. To provision a development admin without a prompt, set `BOOTSTRAP_ADMIN_ENABLED=true`, `BOOTSTRAP_ADMIN_USERNAME` and `BOOTSTRAP_ADMIN_PASSWORD` in that ignored file. Bootstrap creates the named admin only when that username is absent, even if other users exist; later starts never reset its password or permissions. The password must have at least 6 characters and at most 72 UTF-8 bytes. Existing `.env` values are preserved; replace template placeholders before running. Existing database volumes require their original password.

For later starts, use the same command:

```powershell
.\scripts\dev\Start-Development.ps1
```

For IDE/manual startup, export the variables documented in `backend/.env.example`; Spring does **not** automatically read `.env` files. `JWT_SECRET` must be base64 of at least 32 randomly generated bytes. Run `mvn spring-boot:run` from `backend/` with JDK 21. Disable bootstrap outside local development.

`GET http://localhost:8080/actuator/health` returns minimal backend/database health. Flyway initializes identity/capability tables, auth events and Cash/Bank/Other payment methods. Sign in with your provisioned account; admins with user-management permission can create accounts and assign roles and individual permissions in the user directory. Tokens remain in memory, so refreshing the browser requires login again. Sign-out revokes all of the user's sessions. See [API documentation](docs/api/authentication.md).

```powershell
cd backend
mvn --batch-mode --no-transfer-progress verify
```

Backend tests use Testcontainers and need Docker running. They create an isolated PostgreSQL database, apply Flyway migrations and verify bootstrap, login, capability restrictions, live permission changes, inactive accounts, expired/invalid tokens, logout and language persistence. They do not modify your development database.

If Maven was downloaded by the initial setup, the ignored local copy is available at `.tools/apache-maven-3.9.11/bin/mvn.cmd`; it is a convenience, not a committed dependency. In CI, Maven is supplied by the runner.

## Master-data screens

After signing in, use the workspace links for Products, Customers, Suppliers, Container types, Payment methods and Expense categories. Admins can add/edit records and deactivate them using the Active checkbox. Employee access follows workflow capabilities; employees cannot edit reference data through these management screens.

Products enforce kg for spices and pieces for honey. Phone numbers are optional for customers; formatted duplicates offer selection of the existing customer. The walk-in customer is protected. To deactivate the default payment method, first set another active method as default.

Form drafts are stored in IndexedDB per user and survive closing the form or signing in again. Saving still requires a backend connection; these forms do not queue offline writes. Stale edits are rejected with a conflict message. Draft discard is explicit; no accounting history is deleted.

The new Flyway migration runs automatically on backend startup. Backend verification uses disposable PostgreSQL containers; frontend verification includes IndexedDB draft recovery tests.

## Purchase workflow

Restart the backend to apply Flyway V4, then sign in and choose **New purchase**. Add an active supplier and products through the master-data screens first; admins can also create a supplier inline without losing invoice input.

Add kg/piece lines, costs, optional supplier reference/notes and Paid now. Cash is the initial default payment method. Save creates one invoice, stock movements, weighted average costs and any payment/allocation atomically. View **Purchase invoices**, **Supplier balances** and **Inventory** from the workspace. Supplier balances link to that supplier's invoice history. WAC visibility requires COST_VIEW.

Purchase drafts survive refresh and reauthentication. After a network interruption, use **Retry the same purchase**; the exact submitted payload and request key are preserved to prevent duplicates. A final invoice number appears only after server confirmation. Purchase details offer a PDF download. Background automatic synchronization and historical invoice edits remain open.

Inventory is calculated, not guaranteed physical stock. Purchases against negative stock or positive stock with unknown cost require review before valuation; no cost is invented. See [purchase transaction decisions](docs/decisions/0003-purchase-transactions.md).

To bring old goods into the system, open **Inventory → Add old goods** (requires `INVENTORY_ADJUST`). Choose an existing product and enter its physical quantity, estimated unit cost, date, and a reason. The adjustment increases calculated stock and updates weighted average cost, with a movement and audit record. It does not create a purchase invoice or supplier balance. Record each batch once; if the connection fails during save, use **Retry same entry** to avoid a duplicate. This form requires the backend to be online.

Admins can permanently remove an erroneous sale, purchase, payment, expense, waste entry, or opening-stock adjustment from its record page. A reason and confirmation are required. The record disappears from normal history, while a snapshot and deletion reason remain in Audit history. Deletion reverses stock effects transactionally; it is refused when later stock movements or linked payments depend on the record. A paid invoice or payment must first go through the cancellation/refund flow. Remove dependent payment records before deleting their invoice. This action cannot be undone, and backups should be retained.

The supplier on **New purchase** and the type on **New expense** each use one searchable selection field: start typing, then choose the matching result. The choice stays visible in that same field. Expense recorders can also select **New expense type** on the entry page; the new type is selected as soon as it is saved.

**Record waste** uses the same search-and-select field for products. An inventory-adjustment user can choose **New product** there, enter its name, unique code, category, unit and selling price, and use it immediately in the waste entry. Creating the product alone does not add stock; use opening stock for old goods already on hand.

## Supplier payments

Restart the backend to apply Flyway V5, then sign in again. Admins can choose **New supplier payment**, select a supplier (including inactive suppliers with debt), enter an amount and select manual allocation or oldest-invoice-first allocation. Manual allocations must equal the payment; excess payments are rejected. Saving updates invoice status, balances and audit history atomically.

**Supplier payment history** includes both standalone payments and payments made with purchases. Supplier balances link to payment history. Payment drafts survive refresh and reauthentication; use **Retry the same payment** after uncertain network outcomes. There is no automatic submission, payment editing, cancellation or unallocated supplier credit. See [payment API](docs/api/supplier-payments.md) and [allocation decisions](docs/decisions/0004-supplier-payment-allocation.md).

## Sales workflow

Restart the backend to apply Flyway V6. Admins and employees can open **New sale**, select a customer or leave the default walk-in customer, and mix weight products, piece products and anonymous spice containers. Weight products support kg or requested money amount; line prices can be overridden without changing defaults. Use **Pay full total** for a fully paid sale. Partial payment requires a named customer.

Sales save invoice, payment facts, stock movements, cost snapshots and audit records together. Negative calculated stock is allowed with a warning. Anonymous containers record revenue without deducting any specific spice or inventing cost. **Sales invoices** and **Customer balances** are available from the workspace. Cost details require COST_VIEW.

Drafts survive refresh/relogin. Choose **Queue sale** to save a completed sale locally and synchronize it automatically while connected and signed in. Use the sync panel for status, retries and validation corrections. New Sale supports quick customer creation with optional phone and a single search/select field; customer creation requires a connection. Sale details offer a PDF download and a guarded cancellation workflow. Historical invoice editing remains open. See [sales API](docs/api/sales.md) and [sales decisions](docs/decisions/0005-sales-transactions.md).

## Customer payments

Restart the backend to apply V7, then sign in again. Admins can use **New customer payment** to settle a named customer balance manually or oldest-invoice-first. Overpayments and duplicate retries are prevented. Inactive customers can settle debt; walk-in customers cannot receive standalone payments.

Customer balances and sales statuses update together. Sales details show the original payment separately from later allocations, and **Customer payment history** lists standalone payments. Drafts survive refresh/relogin and offer manual retry after uncertain outcomes. See [customer-payment API](docs/api/customer-payments.md).

## Offline sales

Sign in online and expand **Offline sales and synchronization**. Wait for the cache-ready timestamp, or choose **Refresh offline records**. Products/prices, customers, container types and payment methods are cached per user. If the connection fails, selectors use cached records and display their age.

Choose **Queue sale** to persist a completed sale before sending. You can start another sale while it is pending. The panel shows Pending, Syncing, Synced or Needs attention, with server explanations and retry actions. Validation-rejected entries can be reopened for correction; finish any other unsaved draft first.

Synchronization resumes when the backend and the user's session reconnect while the app is open. If the backend is unavailable on reopen or at token renewal, the last signed-in account can use an offline sales workspace with cached records. New Sale can save a new customer locally while offline; when that sale syncs, the server creates the customer using a stable request ID before sending the invoice. A duplicate phone or rejected customer leaves the sale in Needs attention for correction. The access token is never saved locally; only a limited non-secret account profile is kept on this browser. Queued sales stay local until a valid session returns, and clearing browser storage removes them. A server 401 removes offline access. Other workflows retain manual save/retry. Service-worker background submission is not included. See [offline decisions and acceptance limits](docs/decisions/0006-offline-sales.md).

## Expenses and waste

Restart the backend to apply V8. Admins can open **Expenses** or **Waste records** from the workspace, create entries, and filter history by inclusive date range and category/product. Create an expense category in business records before entering the first expense.

Expenses record category, amount, payment method and notes. Waste records product, quantity and reason, reduces calculated stock and preserves current cost without changing WAC. Piece quantities must be whole. Negative stock produces a warning; unknown cost remains unknown. Cost visibility requires COST_VIEW.

These forms preserve drafts and exact submitted requests for manual retry. They are not automatically synchronized by the sales outbox. Editing/reversal and exports remain future work. See [expense/waste API](docs/api/expenses-and-waste.md) and [transaction decisions](docs/decisions/0007-expenses-and-waste.md).

## Configuration and data safety

Only `.env.example` templates belong in Git. All `VITE_*` values are public. Frontend API calls use `VITE_API_BASE_URL` (default `/api`). Health uses the same-origin `/actuator/health` path. The Vite dev proxy forwards both to port 8080. Use same-origin frontend/API routing in production; cross-origin authentication is not configured.

Production uses explicit database environment values and the `prod` Spring profile. Secrets must be injected by the deployment environment. Local Compose credentials must not be reused in production. The laptop deployment now uses local PostgreSQL 18; its files are in `D:\Alanan\Alanan System\The Database`, outside this Git repository. Keep regular backups on another device or offsite, because a disk failure would affect both the app and local database. See [implementation status](docs/implementation-status.md).

Admins can open **Backups** under workspace settings. **Create and download backup** uses the backend's `pg_dump` to make a PostgreSQL custom-format archive and a matching `.dump.sha256` file. **Upload a backup** accepts a `.dump` (up to 512 MB), optionally compares a supplied SHA-256 checksum, checks archive readability and required tables, and stages the file without changing the live database. The page lists staged files with their checksums and allows downloading the archive and matching checksum separately, or removing the staged file. Keep both downloaded files together with their original names and run `scripts/backup/Test-Restore.ps1 -Archive <path-to-dump>` to test a restore in a disposable database before relying on the backup. Set `BACKUP_STAGING_DIRECTORY` to a private persistent folder; the default is `./backups/staged` relative to the backend process. `pg_dump` and `pg_restore` must be on the backend's PATH, or set `PG_DUMP_COMMAND` and `PG_RESTORE_COMMAND`. Keep a downloaded copy off this computer. The app does not replace the current database from the browser.

Each saved backup also has **Test restore**, which runs a disposable PostgreSQL 18 restore and records when it passed. For recovery into a separate empty database, follow [backup recovery](docs/deployment/backup-recovery.md). The current live database is never overwritten by the Backups page.

CI builds/tests both applications and lints the frontend. No commits or deployments are automatically made by local setup.

If backend port 8080 is occupied, set `SERVER_PORT=8081` in the root `.env`. The development helper and Vite proxy both use it. Restart both processes after changing this value; health then uses `http://localhost:8081/actuator/health`.

## Laptop deployment with local PostgreSQL

Start Docker Desktop, then start the `alanan-local-postgres18` container if it is stopped: `docker start alanan-local-postgres18`. From this repository, run `powershell -ExecutionPolicy Bypass -File .\scripts\deploy\Start-Anywhere.ps1`. The ignored root `.env` connects the backend to `127.0.0.1:15433/alanan`. Its database credentials and the prior Neon credentials in `.env.neon` must stay private. The live PostgreSQL files are in the sibling `The Database` folder, so Git cannot push them; `.gitignore` also excludes that folder if it is ever placed inside this repository. See [laptop and mobile deployment](docs/deployment/laptop-mobile.md).

## Optional Neon connection

Set `DB_URL` in the ignored root `.env` to the **direct** Neon JDBC URL (hostname without `-pooler`) with `sslmode=require&channelBinding=require`, and set `DB_USERNAME`/`DB_PASSWORD` separately. This backend needs persistent database sessions for its schema setting; Neon's transaction pooler can lose that setting between queries. The development startup helper automatically substitutes the direct Neon host when the saved URL uses `-pooler`, without editing `.env`. Keep `DB_HOST`, `DB_PORT` and `DB_NAME` consistent with the external database. The startup helper loads these settings and skips local Docker PostgreSQL when an external URL is configured. The backend and frontend still run locally; no Neon application deployment is required.

If reconnecting to Neon later, review the ignored `.env.neon` first and make a fresh local backup before changing `.env`. The JDBC URL must not include credentials; keep them in the separate ignored variables and never in frontend configuration. Changing database URLs does not transfer new records made after the switch.
