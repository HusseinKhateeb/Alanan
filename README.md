# Alanan · محمص العنان

Accounting and business management for Al Anan Roastery. Authentication, master data and purchase invoices with stock/WAC updates and supplier balances are implemented. See [implementation status](docs/implementation-status.md), [purchase API](docs/api/purchases.md), [authentication design](docs/decisions/0002-authentication.md), and [master-data API](docs/api/master-data.md).

## Repository

- `frontend/`: React, TypeScript, Vite, PWA, TanStack Query and Arabic/English localization.
- `backend/`: Java 21, Spring Boot, Spring Security, PostgreSQL and Flyway.
- `docs/specification/Alanan-v6.docx`: supplied product specification.
- `infrastructure/`, `scripts/`: deployment and operational ownership.

## Frontend preview

Install Node 22.12+ (22 LTS recommended), then:

```powershell
cd frontend
npm ci
npm run dev
```

Open the URL Vite prints (normally http://localhost:5173). The Arabic/English login screen needs the backend to sign in. Language selection is saved to the authenticated user's profile. Accepted purchases now create real accounting records in the configured database.

```powershell
npm run lint
npm test
npm run build
npm run preview
```

The service worker is generated for production builds, not the normal dev server. Preview serves the static build; a same-origin reverse proxy is needed for backend reachability in production. Icons are initial monogram placeholders. Device installation/offline acceptance tests remain pending.

## Database and backend

Requirements: JDK 21, Maven 3.9+, Docker Desktop with its Linux engine running.

From the repository root:

```powershell
$env:JAVA_HOME = 'C:\Program Files\Java\jdk-21' # adjust for your JDK
.\scripts\dev\Start-Development.ps1 -BootstrapAdmin
```

The helper creates an ignored root `.env` with random development database/JWT secrets if no file exists, starts PostgreSQL, securely prompts for initial admin credentials, and starts the backend. The password must have at least 14 characters and at most 72 UTF-8 bytes. It is passed only through the process environment, never saved to the file. Admin setup runs only on an empty database and never resets existing users. Existing `.env` values are preserved; replace template placeholders before running. Existing database volumes require their original password.

After initial setup, start normally without the bootstrap switch:

```powershell
.\scripts\dev\Start-Development.ps1
```

For IDE/manual startup, export the variables documented in `backend/.env.example`; Spring does **not** automatically read `.env` files. `JWT_SECRET` must be base64 of at least 32 randomly generated bytes. Remove bootstrap variables after provisioning. Run `mvn spring-boot:run` from `backend/` with JDK 21.

`GET http://localhost:8080/actuator/health` returns minimal backend/database health. Flyway initializes identity/capability tables, auth events and Cash/Bank/Other payment methods. Sign in with your provisioned account; admins can open the read-only user directory. Tokens remain in memory, so refreshing the browser requires login again. Sign-out revokes all of the user's sessions. See [API documentation](docs/api/authentication.md).

```powershell
cd backend
mvn --batch-mode --no-transfer-progress verify
```

Backend tests use Testcontainers and need Docker running. They create an isolated PostgreSQL database, apply Flyway migrations and verify bootstrap, login, capability restrictions, live permission changes, inactive accounts, expired/invalid tokens, logout and language persistence. They do not modify your development database.

If Maven was downloaded by the initial setup, the ignored local copy is available at `.tools/apache-maven-3.9.11/bin/mvn.cmd`; it is a convenience, not a committed dependency. In CI, Maven is supplied by the runner.

## Master-data screens

After signing in, use the workspace links for Products, Customers, Suppliers, Container types, Payment methods and Expense categories. Admins can add/edit records and deactivate them using the Active checkbox. Employee access follows workflow capabilities; employees cannot edit reference data through these management screens.

Products enforce kg for spices and pieces for honey. Phone numbers are optional for customers; formatted duplicates offer selection of the existing customer. The walk-in customer is protected. To deactivate the default payment method, first set another active method as default.

Form drafts are stored in IndexedDB per user and survive closing the form or signing in again. Saving still requires a backend connection; these forms do not queue offline writes. Stale edits are rejected with a conflict message. Draft discard is explicit; no accounting history is deleted.

The new Flyway migration runs automatically on backend startup. Backend verification uses disposable PostgreSQL containers; frontend verification includes IndexedDB draft recovery tests.

## Purchase workflow

Restart the backend to apply Flyway V4, then sign in and choose **New purchase**. Add an active supplier and products through the master-data screens first; admins can also create a supplier inline without losing invoice input.

Add kg/piece lines, costs, optional supplier reference/notes and Paid now. Cash is the initial default payment method. Save creates one invoice, stock movements, weighted average costs and any payment/allocation atomically. View **Purchase invoices**, **Supplier balances** and **Inventory** from the workspace. Supplier balances link to that supplier's invoice history. WAC visibility requires COST_VIEW.

Purchase drafts survive refresh and reauthentication. After a network interruption, use **Retry the same purchase**; the exact submitted payload and request key are preserved to prevent duplicates. A final invoice number appears only after server confirmation. Background automatic synchronization, historical invoice edits and PDF exports are not included yet.

Inventory is calculated, not guaranteed physical stock. Purchases against negative stock or positive stock with unknown cost require review before valuation; no cost is invented. See [purchase transaction decisions](docs/decisions/0003-purchase-transactions.md).

## Supplier payments

Restart the backend to apply Flyway V5, then sign in again. Admins can choose **New supplier payment**, select a supplier (including inactive suppliers with debt), enter an amount and select manual allocation or oldest-invoice-first allocation. Manual allocations must equal the payment; excess payments are rejected. Saving updates invoice status, balances and audit history atomically.

**Supplier payment history** includes both standalone payments and payments made with purchases. Supplier balances link to payment history. Payment drafts survive refresh and reauthentication; use **Retry the same payment** after uncertain network outcomes. There is no automatic submission, payment editing, cancellation or unallocated supplier credit. See [payment API](docs/api/supplier-payments.md) and [allocation decisions](docs/decisions/0004-supplier-payment-allocation.md).

## Sales workflow

Restart the backend to apply Flyway V6. Admins and employees can open **New sale**, select a customer or leave the default walk-in customer, and mix weight products, piece products and anonymous spice containers. Weight products support kg or requested money amount; line prices can be overridden without changing defaults. Use **Pay full total** for a fully paid sale. Partial payment requires a named customer.

Sales save invoice, payment facts, stock movements, cost snapshots and audit records together. Negative calculated stock is allowed with a warning. Anonymous containers record revenue without deducting any specific spice or inventing cost. **Sales invoices** and **Customer balances** are available from the workspace. Cost details require COST_VIEW.

Drafts survive refresh/relogin. Choose **Queue sale** to save a completed sale locally and synchronize it automatically while connected and signed in. Use the sync panel for status, retries and validation corrections. Completed-sale editing/refunds and PDF exports are not implemented. See [sales API](docs/api/sales.md) and [sales decisions](docs/decisions/0005-sales-transactions.md).

## Customer payments

Restart the backend to apply V7, then sign in again. Admins can use **New customer payment** to settle a named customer balance manually or oldest-invoice-first. Overpayments and duplicate retries are prevented. Inactive customers can settle debt; walk-in customers cannot receive standalone payments.

Customer balances and sales statuses update together. Sales details show the original payment separately from later allocations, and **Customer payment history** lists standalone payments. Drafts survive refresh/relogin and offer manual retry after uncertain outcomes. See [customer-payment API](docs/api/customer-payments.md).

## Offline sales

Sign in online and expand **Offline sales and synchronization**. Wait for the cache-ready timestamp, or choose **Refresh offline records**. Products/prices, customers, container types and payment methods are cached per user. If the connection fails, selectors use cached records and display their age.

Choose **Queue sale** to persist a completed sale before sending. You can start another sale while it is pending. The panel shows Pending, Syncing, Synced or Needs attention, with server explanations and retry actions. Validation-rejected entries can be reopened for correction; finish any other unsaved draft first.

Synchronization resumes on reconnect and runs while the app is open and signed in. After reopening or session expiry, reconnect and sign in; tokens are not saved locally. Queued sales survive refresh/restart, but clearing browser storage removes local work. Other workflows retain manual save/retry. Offline customer creation and service-worker background submission are not included. See [offline decisions and acceptance limits](docs/decisions/0006-offline-sales.md).

## Expenses and waste

Restart the backend to apply V8. Admins can open **Expenses** or **Waste records** from the workspace, create entries, and filter history by inclusive date range and category/product. Create an expense category in business records before entering the first expense.

Expenses record category, amount, payment method and notes. Waste records product, quantity and reason, reduces calculated stock and preserves current cost without changing WAC. Piece quantities must be whole. Negative stock produces a warning; unknown cost remains unknown. Cost visibility requires COST_VIEW.

These forms preserve drafts and exact submitted requests for manual retry. They are not automatically synchronized by the sales outbox. Editing/reversal and exports remain future work. See [expense/waste API](docs/api/expenses-and-waste.md) and [transaction decisions](docs/decisions/0007-expenses-and-waste.md).

## Configuration and data safety

Only `.env.example` templates belong in Git. All `VITE_*` values are public. Frontend API calls use `VITE_API_BASE_URL` (default `/api`). Health uses the same-origin `/actuator/health` path. The Vite dev proxy forwards both to port 8080. Use same-origin frontend/API routing in production; cross-origin authentication is not configured.

Production uses explicit database environment values and the `prod` Spring profile. Secrets must be injected by the deployment environment. Local Compose credentials must not be reused in production. There is no production deployment or backup workflow yet.

CI builds/tests both applications and lints the frontend. No commits or deployments are automatically made by local setup.

If backend port 8080 is occupied, set `SERVER_PORT=8081` in the root `.env`. The development helper and Vite proxy both use it. Restart both processes after changing this value; health then uses `http://localhost:8081/actuator/health`.

## Local backend with Neon PostgreSQL

Set `DB_URL` in the ignored root `.env` to the Neon JDBC URL with `sslmode=require&channelBinding=require`, and set `DB_USERNAME`/`DB_PASSWORD` separately. Keep `DB_HOST`, `DB_PORT` and `DB_NAME` consistent with the external database. The startup helper loads these settings and skips local Docker PostgreSQL when an external URL is configured. The backend and frontend still run locally; no Neon application deployment is required.

Run `scripts/dev/Start-Development.ps1` normally, or add `-BootstrapAdmin` when the database has no users yet. Startup applies Flyway migrations to the configured Neon database. The JDBC URL must not include credentials; keep them in the separate ignored variables and never in frontend configuration. Changing databases does not transfer existing local records.
